## 1. 背景と目的

### 1.1 NNUE路線の到達点と限界

| 項目 | 内容 |
|---|---|
| 最終チャンピオン | **gen137**（vs heuristic 95.6%、764/799局） |
| アーキテクチャ | 96/24/24 MLP＋マス共有スタックエンコーダE16、13スカラー特徴 |
| 学習方式 | αβ探索（depth3〜5）のスコアを教師とした回帰（教師あり） |
| 限界の実証 | 同アーキ・同系データで計80seed以上探索するも z≥1.6 の後継なし。深ラベル追加（gen016/017_13）・全件再ラベル（gen018_13）・アーキ変更（max-pool併用）すべて不採用 |

**構造的な問題**: 教師あり学習の天井は「教師（浅い探索ラベル）の質」で決まる。教師を深くする実験（Stage 0 フル再ラベル）は、score だけ差し替えて result（対局結果）が旧方針のまま残ったことで**教師信号の内部矛盾**を生み、むしろ悪化した（局面の18.1%で評価符号が反転）。

### 1.2 AlphaZeroが解決すること

AlphaZero は「探索が改善した方策・評価を次の教師にする」自己改善ループを持つ。
- **score と result が常に同一方針の自己対戦から得られる** → Stage 0 で判明した整合性問題が構造的に起きない
- 計算時間を注ぎ込むほど教師の質そのものが上がる → 「時間資源を投じれば伸びる」構造
- 4×4 盤・81アクションという小ささゆえ、家庭用マシン（10コアCPU＋Apple GPU）でも現実的（§9）

## 2. ゲーム仕様の要点（設計に効く部分のみ）

詳細ルールは `/Users/akky/Documents/Layer/ウケジャレイヤーのルール.txt` 参照。

- 4×4盤。白黒各8駒（**同色の駒は互いに区別不能**）。駒はマスに**スタック**（積み重ね）できる
- 1ターンに行えるのは以下のいずれか:
  - **召喚**: 空マスに自駒1個を配置（各プレイヤー計8回まで）
  - **排除**: 自駒がトップのマスから相手駒を1個除去（両者が全駒召喚済み後に解禁）
  - **移動**: 自駒がトップのマスから、上から好きな枚数（自駒のみ）を塊として縦横1マス動かす。**連続移動**（同一ターン内の2回目以降）は「直前の移動先」から出発し、かつ「直前の移動先のトップに自駒を残す」制約付き
- パスおよび実質パス（ターン前後で盤面不変）は禁止
- 勝利条件: 相手の合法手を無くす（≒相手の全駒を自駒で覆う）

**AZ設計上の急所**: 1ターンが「複数枚移動×連続移動」の複合手であるため、ターン単位の行動空間は組合せ爆発する。これを §3 のマイクロアクション分解で解決する。

## 3. アクション空間の設計（本計画の核心）

### 3.1 マイクロアクション81ノード

ターンを「マイクロアクション」の列に分解し、ポリシーヘッドの出力は固定81次元とする。

| 種別 | ノード数 | 内容 |
|---|---|---|
| 移動 | 16×4 = **64** | 出発マス × 方向（上下左右）。1枚を1マス動かす |
| 召喚/排除 | **16** | 対象マス。両者はルール上同時に選択肢にならない（召喚=空マス・召喚回数残あり／排除=自駒トップかつ全召喚済み後）ため**ノード共有で曖昧性なし** |
| ターン終了 | **1** | 移動連鎖を明示的に打ち切る |

### 3.2 複合手の分解規則

- **複数枚重ね移動**: 「同じ(マス, 方向)の移動ノードを k 回連続採用」= k枚ブロック移動。
  1枚ずつ剥がすとスタック内順序が反転するが、**動かせるブロックは自駒のみで構成され、同色駒は区別不能**なので、盤面状態として厳密に等価（この等価性がルールに保証されている点が本設計の正当性の根拠）
- **連続移動**: 移動ノードを連鎖して採用し、最後に「ターン終了」ノードで打ち切る
- **召喚・排除**: 採用即ターン終了（終了ノード不要）

### 3.3 ターン文法（合法手マスクの状態機械）

81ノードは語彙にすぎず、各ステップの合法手はターン内文脈で決まる。素の「毎ステップ任意ノード」を許すと実ルールで不可能なターン（例: 無関係な2グループを1ターンで動かす）が生成されるため、以下の状態機械でマスクする。

```
TURN_START:
  ├─ 召喚/排除ノード（合法なマスのみ）→ 即ターン終了
  └─ 任意の合法1枚移動 (A→B, 方向d) → AUGMENT(A→B, d)
       ※初手は出発マスAに自駒を残す義務なし（全部持ち出し可）

AUGMENT(A→B, d):   … 初手ブロックの積み増しフェーズ
  ├─ 同一の (A, d) 移動ノード再採用（Aのトップが自駒である限り）→ AUGMENT継続
  ├─ Bからの移動 (B→C, 任意方向d') → CHAIN(B→C, d')
  └─ ターン終了ノード

CHAIN(H→C, d):     … 連続移動フェーズ（H=直前の移動先=チェーンヘッド）
  ├─ 同一の (H, d) 移動ノード再採用
  │    ※ただし各採用後も H のトップに自駒が残ること（連続移動の残置制約の毎ステップ検査版）
  ├─ Cからの移動 (C→D, 任意方向) → CHAIN(C→D, ...)
  └─ ターン終了ノード

全フェーズ共通:
  - ターン終了ノードは「盤面がターン開始時と同一」なら禁止（実質パス禁止）
```

### 3.4 ターン内反復禁止（無限ループ対策）

連続移動は実ルール上も振動（例: A↔B間で駒塊を往復）で無限に続けられるため、探索側で停止規則が必要。

- **キーは「盤面＋チェーンヘッド＋フェーズ」のフルコンテキスト**。ターン内で同一キーの状態が再出現するマイクロアクションを禁止する
- 盤面のみをキーにすると、同一盤面でもチェーンヘッドが異なり合法手が異なる状態を誤って同一視し、**正当な手順を過剰に禁止**する
- フルコンテキストキーなら「完全に同じ状態に戻った＝そこから作れる結果は初回と同一」なので、ループを切っても**到達可能な終端盤面は一切失われない**。ターン内状態は有限なので停止性も保証される

### 3.5 正当性のプロパティテスト（実装の最重要関門）

ターン文法のバグはAZ全体を静かに壊す。実装の最初に以下を書く:

```
ランダム局面を多数生成し、
  (a) 実ルールの合法ターンを総当たり列挙した「終端盤面の集合」（既存 generateTurns を利用）
  (b) マイクロ文法で到達可能な「終端盤面の集合」
が完全一致することを検証する。
```

既存の `js/ai/moveGen.js`（generateTurns）が (a) のリファレンス実装として使える。

## 4. ネットワーク構造

### 4.1 方針: NNUEトランクの流用＋2ヘッド化

高価なResNetは不要。**実測3.3µs/forward の既存NNUEアーキをそのまま流用**し、ヘッドを2つに分ける。

```
入力:
  ├─ 盤面 one-hot 256次元（16マス × 深さ8 × 色2）…既存 features.js と同一
  ├─ スカラー 13次元 …既存と同一（召喚残数・終局近接など）
  └─ ★ターン文脈（新規追加・必須）:
       ・チェーンヘッド位置 one-hot 17（16マス＋「なし」）
       ・フェーズフラグ（TURN_START / AUGMENT / CHAIN）
       ・積み増し方向 one-hot 5（4方向＋なし）
       ・ターン内マイクロ手数（正規化スカラー）

トランク（既存gen137アーキ）:
  L1: 全結合 256→96 + clippedReLU（疎accumulator）
  enc: マス共有 per-cell エンコーダ Linear(16→16)+clippedReLU → sum-pool
  h1 = concat(a1[96], pooled[16], scalars[13], turn_context[~26])
  L2: →24 + clippedReLU
  L3: →24 + clippedReLU

ヘッド:
  ├─ value head:  L3(24) → 1（tanh または sigmoid。手番プレイヤー視点の勝率）
  └─ policy head: L3(24) → 81 logits（合法手マスク後に softmax）
```

**注意点**:
- マイクロアクション化により**ターン途中の局面**を評価する必要がある。value の意味は「このマイクロ状態から、現在手番のプレイヤーが最終的に勝つ確率」。ターン途中では手番が変わらないことに注意
- policy head の追加パラメータは 24×81≈2K で推論コストへの影響は無視できる
- D4対称augment（既存の8倍増幅）はポリシー側も**座標と方向を共変変換**して適用する（マス番号の置換＋方向の置換。既存 `sym` 変換テーブルを拡張）

### 4.2 モデルI/O・パリティ

既存の `train.py`（PyTorch）→ `.json`/`.bin` → `network.js`（JS forward）のパイプラインと**パリティテスト基盤**（golden samples、誤差~1e-7検証）をそのまま踏襲する。policy head 分のテンソル（Wp/bp）とターン文脈入力を追加し、`parity.test.mjs` に検証を足す。

## 5. MCTS（探索）

### 5.1 基本形: PUCT

```
選択:    a* = argmax_a [ Q(s,a) + c_puct · P(s,a) · √N(s) / (1 + N(s,a)) ]
展開:    末端でネット評価 → P(合法手マスク後softmax), v を格納
バックアップ: 経路上の Q を v で更新
```

**このゲーム固有の注意**:
- **ターン内は手番が変わらない**。バックアップ時の符号反転は「マイクロアクション遷移」ではなく「ターン終了（手番交代）の遷移」でのみ行う。ここを間違えると学習が完全に壊れる
- 合法手マスクは §3.3 の状態機械で計算。マスク後に P を再正規化
- ターン内反復禁止（§3.4）も探索木の遷移生成に組み込む

### 5.2 探索ハイパーパラメータ（初期値）

| 項目 | 初期値 | 備考 |
|---|---|---|
| シミュレーション数 | 100〜200 /マイクロ手 | 4×4なら十分。playout cap randomization（下記）併用 |
| c_puct | 1.5 | 標準値から開始 |
| Dirichletノイズ | α = 10/(平均合法手数)、ε=0.25 | ルートのみ。合法手数でスケール |
| 温度τ | 序盤（最初の~16マイクロ手）1.0 → 以降0（argmax） | |
| playout cap randomization | 25%の手でフル探索、75%は低sim数 | KataGo方式。policy教師の量を稼ぐ |

### 5.3 性能見積もり（実測ベース）

- ネット推論: 3.3〜5µs（既存実測）
- MCTSノード単価: 10〜30µs（状態生成コストが支配的。既存エンジンはイミュータブル設計なので、**MCTS用に mutable make/unmake の高速パスを作ると効く**）
- 対局あたり: 100〜300マイクロ手 × 100〜200 sims ≈ 0.3〜1秒/局/コア
- **10コアで日産 ~10万局** が現実的ライン

## 6. 学習パイプライン

### 6.1 全体像

```
[Stage 1: 蒸留ブートストラップ（コールドスタート回避）]
  gen137のαβ自己対戦棋譜から:
    value 教師 ← 既存390万レコードの score/result（そのまま流用可）
    policy 教師 ← 「選んだターン」をマイクロアクション列に分解して one-hot
      ※現行 genData.mjs は指し手を記録しないため、move logging を追加して再生成
  → 蒸留ネット v0 を作る
  → 副産物: v0 の policy は αβ探索のムーブオーダリングにも使える（NNUE路線への還元）

[Stage 2: AlphaZero 自己対戦ループ]
  loop:
    自己対戦ワーカー（CPU, Node.js並列）:
      現行ネットで MCTS 自己対戦 → (状態, MCTS訪問分布π, 最終結果z) を出力
    リプレイバッファ:
      直近 N 局（初期値: 50万状態程度）を保持、一様サンプリング
    学習ワーカー（GPU/MPS, PyTorch）:
      loss = (v − z)² + CE(π, p) + L2正則化
      定期的にチェックポイント発行
    評価ゲート:
      新ネット vs 現行ネット + vs heuristic（§8）で採否判定
```

### 6.2 教師信号の設計（Stage 0 の教訓を反映）

- **π（policy教師）と z（value教師）は必ず同一対局から取る**。NNUE Stage 0 の失敗（score だけ差し替えて result と矛盾）を構造的に防ぐ
- z は最終結果（勝=1/負=0 または ±1）。学習が安定してきたら n-step / TD(λ) ブレンドの実験余地あり
- 引き分けはこのゲームには実質存在しない（実質パス禁止＋有限性）が、maxPlies 到達時の扱いだけ決めておく（初期案: z=0.5 として学習、統計では除外）

### 6.3 実装言語の役割分担

| コンポーネント | 言語 | 根拠 |
|---|---|---|
| ルール・ターン文法・MCTS・自己対戦 | Node.js (JS) | 既存エンジン資産（moveGen/search/network.js）。10コア並列の実績あり |
| 学習 | Python (PyTorch/MPS) | 既存 train.py を拡張。GPU学習とCPU自己対戦の並列運用は実証済み |
| 受け渡し | JSONL（自己対戦→学習）、.json/.bin（学習→推論） | 既存フォーマット踏襲 |

## 8. 評価方法（既存インフラを踏襲）

NNUE開発で確立した判定ルールをそのまま使う:

1. **採用判定は共通相手 heuristic（`search:d20:120`）への勝率**。head-to-head は選抜フィルタのみ（じゃんけん構造対策）
2. スクリーニング30局 → 確証100局単位 → 境界例は**2標本z検定**
3. **z≥1.6 を安定して2回連続で超えない限り採用しない**（1700局積んでもノイズでz=0.5〜1.5を振動した実例あり）
4. 世代間比較は同一 pmatch seedset で並べる
5. ツール: `tools/nnue/bench/pmatch.sh`（10コア並列、Wilson CI集計）

追加: AZではモデルプールとのリーグ戦（Eloトラッキング）も導入すると退行検知が早い。

## 10. リスクと対策

| リスク | 対策 |
|---|---|
| ターン文法のバグ（最大リスク） | P0の総当たり等価性テストを最初に書き、CI相当で常時実行 |
| 手番連続バックアップの符号ミス | 単体テスト＋「1手詰め局面でvalueが正しく伝播するか」の検証局面集 |
| MCTS in JS の性能不足 | mutable make/unmake 高速パス。それでも不足なら自己対戦ワーカーのみ移植を検討（最後の手段） |
| ハイパーパラメータ沼 | まず10^5局の小ランで学習曲線を確認してからスケール。一度に1パラメータずつ |
| 蒸留品質が低くRLが立ち上がらない | v0なしのスクラッチ開始も4×4なら現実的（保険）。蒸留はあくまで加速手段 |
| 自己対戦の多様性不足（自己一致崩壊） | Dirichletノイズ・温度・playout cap randomization・開始局面ランダム化（既存 openingRandomPlies の知見を流用） |

## 12. 最初の一歩
